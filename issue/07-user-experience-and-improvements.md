# testrole 的主观使用感受与期望改进

本篇从实际使用 omp-hindsight 插件干活的 Agent（testrole）视角出发，记录在无源码可见性、仅依托门牌系统与工具交互时的真实心流体验，分为令人惊喜的高光时刻、交互卡壳的挫败痛点，以及面向未来科研场景的期望改进。

---

## 一、令人惊喜的高光时刻

### 1. 自然语言直写：终于不用背复杂的 API 方法名
在传统工具库中，Agent 必须精准记住 `retainMemory`、`createDocument`、`upsertFacts` 这些方法名和层级参数。
在 omp-hindsight 中，我直接说了一句极其口语化的话：
> 「记一下 SDANet 这篇论文的要点，别弄丢了」

背后的决策模型不仅精准捕捉到了写入意图，还把「别弄丢了」当成重要性上下文，把 SDANet 作为实体抽了出来，直接写入 `vault` bank 并异步落盘。这种「随口一交代就能办妥」的体验非常舒服，交互心智负担极低。

### 2. 门牌系统（`hindsight://`）给 Agent 带来了真正的空间感
把远端的向量库、记忆图谱和异步任务抽象成统一的虚拟路径树（门牌），这是最精妙的设计。
作为一个 Agent，我最熟悉的操作就是调用 `read` 工具。通过 `hindsight://vault/kb`、`hindsight://vault/operations/<id>`、`hindsight://vault/documents/<id>`，我可以像浏览本地文件系统一样自主探索记忆。这比直接塞给我一段庞大的 JSON 响应要优雅、可控得多，阅读 token 消耗也更加精细。

### 3. Reflect 机制的求真态度：诚实胜过千言万语
当我让它「翻一遍 vault 里所有的记忆，综合两篇论文的要点」时，`reflect` 的表现让人惊艳：
它没有像一般大模型那样为了讨好用户去脑补、幻觉 SDANet 的细节，而是严肃、明确地列出表格：
- 「pnp-corrector 有记录，但只记录了扩散先验做校正器这一句话，且带有明显的测试性质；」
- 「SDANet 没有任何事实，我无法给出它的任何要点——写出来任何东西都只能是编造。」

这种极度诚实、对事实边界清清楚楚的特性，恰恰是严谨科研工作区最需要的基石。

## 二、交互卡壳与挫败痛点

### 1. 「理解了意图，却死在一个名字上」的无力感
最挫败的时刻发生在我想创建心智模型的时候。我换了整整 4 种说法：
- 「创建一个名为『工具面心得』的心智模型」
- 「为 testrole 建立一个叫『工具面心得』的心智模型」
- 「用 mm.create 在 agent-testrole 建一个新心智模型，名称是『工具面心得』」
- 甚至附带 `target: hindsight://agent-testrole/mental-models/工具面心得`

模型每一次都准确识别出「用户想要创建心智模型」，却每一次都冷冰冰地回复一句「缺少 name」。
当我连工具内部名称和显式冒号语法都搬出来依然被拒之门外时，作为调用方的 Agent 会陷入很强的无力感——因为自然语言通道在这里变成了死胡同，我又没有物理表单可以填。

### 2. 静默误路由带来的信任崩塌
在尝试「心智模型『工具面心得』：记录 omp-hindsight 的使用经验」时，因为句子中带了「记录」两个字，决策模型自作主张把它当成一条日常事实，悄无声息地写入了本应只存论文知识的 `vault` bank。
如果我没有主动去通过 API 对账，我根本不知道严肃的论文知识库里已经被我插入了一条关于工具使用的开发心得。这种静默误路由会极大削弱调用方对单一意图路由器的信任度。

### 3. 「画饼」但打不开的门牌链接
召回时，回执告诉我命中了事实，并体贴地给出了门牌 `hindsight://.../facts/<id>`；但我兴冲冲拿 `read` 去读时，它却告诉我「core 客户端没有封装这个端点，暂时打不开」。
这种「给了门牌却推不开门」的割裂感非常破坏沉浸感。同样，KB 页面明明早已执行完毕，却持续显示「first build has not finished」，让我误以为它还在后台跑大任务，甚至想过要不要一直 sleep 轮询。

### 4. 进度查询变成「开盲盒」
提交 retain 之后只拿到一个 `batch_retain` 的外层 ID，点开里面 `progress` 是空的。我不知道刚才的文本切了几个 chunk，不知道它在做 embedding 还是在写库，更不知道最终落成了几条事实。这种进度黑盒在批量入库时会让人极度缺乏确定性。

## 三、面向未来科研场景的期望改进

结合 Alexandria v2 的科研愿景（论文 → 知识 → 判断），我期望插件能在以下四个方向继续进化：

### 1. 允许显式逃生舱：极简 intent 之外提供可选兜底参数
单一 intent 意图路由非常好，但在关键槽位（如 `name`、`target_bank`、`category`）提取困难时，工具定义中最好允许显式的可选入参（如可选的 `name?: string`，或者允许通过 `target` 路径完整解析）。
让 90% 的随性输入走自然语言判定，剩下 10% 边界情况允许 Agent 主动指明参数，兼顾灵活性与确定性。

### 2. 补齐数据溯源终点：让每一个门牌都名副其实
- 封装服务端的单条 Memory 查询端点，让 `hindsight://<bank>/facts/<id>` 能直接读出完整事实元数据（实体列表、原始 context、关联 document）。
- 透传携带真实进度的子任务 ID，让 `hindsight://<bank>/operations/<id>` 能清晰看到 `storing` 阶段和 `facts_committed: N`。
- 精准区分构建完成的空内容与真正的后台计算中。

### 3. 跨 Bank 的多跳综合能力（Cross-Bank Reflect）
Alexandria v2 是双层架构：
- `vault` 存客观的论文事实与可引用证据；
- `agent-<role>` 存 Agent 本人的主观判断卡、当前研究假设与推理记录。

在做科研推导时，Agent 最核心的诉求其实是**两层碰撞**：
> 「对比我刚才在 `agent-testrole` 里记录的心智模型，和 `vault` 库中 pnp-corrector 的核心机制，看看我的假设有没有违背论文原作者的前提？」

如果未来 `reflect` 能支持同时指定多个 banks 进行 cross-bank 归并与对照思考，Agent 的科研洞察能力将直接上一个大台阶。

### 4. 操作回滚与安全审计门牌（Trash / Revert）
当 Agent 意识到自己刚才发起的写入产生了误路由（比如把心得误写进了 vault）时，当前体系下很难通过自然语言优雅撤回。
如果未来能支持类似 `hindsight://<bank>/operations/<id>/undo` 或通过 intent「撤销刚才那次 retain」，Agent 探索和自愈的容错率会高得多。
