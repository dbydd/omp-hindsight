# 回归初心：omp 会话历史（history://）与 Hindsight 可复用知识的正交边界

在设计大语言模型编码助手的记忆系统时，一个长期普遍存在却鲜被深入审视的误区是：**将“会话历史的执行过程回溯”与“沉淀下来的可复用知识”混为一谈**。

在许多简易的 Agent 框架中，记忆系统往往被作为聊天日志的归档数据库使用。本篇文档系统阐述这一做法为何是引发 Agent 能力退化的反模式，并明确 `history://` 与 `Hindsight` 在 `oh-my-pi`（omp）中的正交职责划分。

---

## 一、其他 Harness 误入歧途的根本原因

社区中许多针对 Hindsight 或类似向量记忆系统的插件，均设计了极其复杂的“全量会话自动回写”逻辑：在每轮对话结束或会话切换时，自动抓取未经提炼的原始对话 JSONL 文件，整体推送到记忆库中进行事实抽取。

这一设计在那些简易框架中存在其无奈的现实原因：
- 那些环境自身缺乏完善的会话持久化与状态机回溯机制。
- 一旦终端关闭、进程重启或上下文达到极限发生滚动，Agent 就会彻底丧失对先前执行步骤的感知。
- 因此，它们被迫将 Hindsight 当作外部聊天记录备份盘，试图通过向量相似度检索重新找回刚刚做过的事情。

---

## 二、全量会话倾倒：引发 Agent 能力退化的反模式

在严肃的软件工程与学术研究中，将未经提炼的聊天流水账全量倾倒进记忆系统，会带来灾难性的系统退化：

### 1. 垃圾事实（Junk Facts）淹没高价值知识
一次真实的编程排错会话中，90% 以上的文本由漫长的工具输出、临时的语法探查、走入死胡同的逻辑尝试以及零碎的调试打印构成。
如果将这些内容全量输入 Hindsight 运行事实抽取，记忆库中会被动生成成千上万条低质的垃圾事实（例如“助手在第 4 轮读取了某文件未发现异常”、“用户在 15 点询问测试是否通过”）。

### 2. 向量检索污染与“信息回音壁”
当 Agent 在后续任务中需要查询某个技术栈的设计规范时，混合检索算法极易从这堆废料中召回某次历史排错中为了临时应急写出的半成品代码或错误假设。
Agent 无法有效区分哪些是经过验证的规范，哪些是历史上的试错残渣。它会把过去被证伪的方案当成权威依据，陷入循环试错与能力断崖式退化。

### 3. 架构虚胖与无谓的技术债务
为了防止会话垃圾撑爆向量库，开发者不得不疲于奔命地设计复杂的补偿机制：建立庞大的 `toolFilter` 黑名单排除探查工具、设计字段脱敏与元数据剥除管道、维护复杂的会话状态标记（Pending Marker）并在后台重新反查磁盘文件。这些繁重的机制消耗了大量算力与工程复杂度，却只能在边缘修修补补。

## 三、omp 的天生正交架构：两套系统的清晰分工

`oh-my-pi` 自身拥有极其强大、原生的会话与执行记录基础设施。在 omp 体系下，我们具备完全回归初心的条件，彻底将两者正交解耦：

```
+-------------------------------------------------------------------------+
|                        oh-my-pi (omp) 统一运行时环境                     |
+-------------------------------------------------------------------------+
                                     |
         ┌───────────────────────────┴───────────────────────────┐
         ▼                                                       ▼
【会话历史与工作过程 (omp 原生)】                   【可复用知识与决策外脑 (Hindsight)】
- 协议入口：history://, session://, ctx           - 协议入口：hindsight://
- 数据属性：单次任务的物理执行轨迹与完整流水账     - 数据属性：跨会话长效成立的结论、规约与领域知识
- 存储形式：无损 JSONL Transcript                 - 存储形式：原子事实、观察认知、知识页、心智模型
- 检索方式：精准行号定位、上下文任务树回放         - 检索方式：语义向量相似度、BM25 混合检索、图谱关联
- 适用场景：“我刚才改了哪一行代码？”             - 适用场景：“该项目的向量索引采用什么架构规约？”
           “上一次测试报错的原始堆栈是什么？”                 “先前对于数据库分表的决策依据是什么？”
```

### 1. 会话过程与历史回溯归 `history://`
- 追溯当前任务刚刚执行了什么、查看子代理的完整对话日志、排查历史工具调用的原始输出，直接使用 omp 内置的 `history://current/full`、`history://<id>` 与 `ctx show`。
- 这是确定性、逐字节无损的精确还原，根本不需要经过大模型向量化与二次事实抽取。

### 2. 知识沉淀与规约感知归 `Hindsight`
- Hindsight **只存、只管抽取出来的可复用知识**：
  1. **领域与研究文献**：通过受控 Ingest 管道入库的学术论文与技术专著；
  2. **项目工程规约（Conventions）**：团队达成的架构约定与代码规范；
  3. **关键架构决策（Decisions）**：显式沉淀的技术选型结论与避坑指南；
  4. **高阶认知模型（Mental Models）**：跨越多个任务沉淀出的稳定用户偏好与系统认知。

## 四、回归初心后的精炼架构收益

明确了两者的正交边界后，`hindsight-omp` 插件卸下了沉重的历史包袱，获得了极致的轻量与锐利：

1. **坚决砍掉全量会话自动倾倒**：
   插件彻底删除在 `agent_end` 和 `session_shutdown` 时无脑全量回写会话的机制。会话过程留在 `history://` 中，记忆库坚决不收纳聊天流水账。
2. **Retain 动作的高纯度与神圣性**：
   记忆库的写入聚焦于高价值沉淀。只有当 Agent 或用户显式发出记录指令（例如 `hindsight("记录这项架构决策：...")`），或者后台决策提取器确认产生了一项通用的工程经验时，才以结构化条目形式写入库中。
3. **异步队列大幅简化**：
   队列不再需要管理复杂的双态（Pending Marker vs Session Reparse），完全收敛为针对已确认高价值条目（Tool Entry）的轻量级异步投递管道。
4. **检索结果 100% 高质量**：
   由于库内没有半点聊天废话，Agent 在长程自治编码中通过自适应 Recall 召回的每一条知识，都是高密度的项目规约与黄金避坑指南，真正实现了知识赋能而非认知干扰。
