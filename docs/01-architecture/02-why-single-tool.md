# 为什么收敛为单工具入口：20+ 平铺工具的失败剖析

在设计 `hindsight-omp` 时，核心工程决策是将过去平铺在 Agent 面前的 20 余个分散工具收敛为一个统一的调用入口：

```ts
hindsight(intent: string, meta?: Record<string, unknown>)
```

本篇文档记录这一决策的实测背景、面临的工程失效模式以及对应的解决机制。

## 历史方案（平铺工具模式）的实际运行表现

在早期的记忆插件实现中，记忆系统的全部 API 端点被机械地转换为一组平铺的工具注册到 Agent 提示词中。系统提供了包括 `hindsight_recall`、`hindsight_reflect`、`hindsight_retain`、`hindsight_kb_search`、`hindsight_kb_get`、`hindsight_mm_list` 等多达 24 个独立工具。

长期实测表明，平铺工具模式在长程工程任务中会产生三个严重的系统性失效：

### 1. 上下文提示词预算的严重浪费

大语言模型的工具调用能力依赖于在 System Prompt 中为每个工具注入完整的 JSON Schema 与参数描述。
- 24 个工具的定义占据了超过 3,500 个 Token 的固定上下文空间。
- 在每一轮模型对话中，无论当前任务是否涉及记忆查询，这 3,500 个 Token 都必须全量参与计算。这直接挤压了代码上下文、文件列表和任务指令的可用空间。

### 2. 相似语义边界导致注意力发散与决策瘫痪

大模型在面对大量语义相近的工具名时，极易发生注意力分配发散。
例如，当用户要求“参考之前关于数据库索引的设计规范”时，模型需要从以下几个候选工具中抉择：
- `hindsight_recall`（检索原子事实）
- `hindsight_reflect`（深度合成回答）
- `hindsight_kb_search`（检索结构化知识页）
- `hindsight_mm_get`（读取心智模型）

由于工具描述文本存在天然的交叉，模型难以在单次推理中建立严格的操作分界。实际观察到的现象包括：
- 模型因不确定选择哪个工具而选择放弃调用，退化为直接凭幻觉生成答案。
- 模型在第一步选错工具，例如调用了要求提供具体 ID 的 `hindsight_kb_get`，并在缺少 ID 的情况下随机捏造一个空字符串或通配符导致报错。

### 3. 多工具维护破坏了单一职责原则

每一个平铺工具都需要独立声明自己的入参校验、鉴权逻辑和错误格式化。这导致插件内部充斥着大量重复的胶水代码，增加了单点失败的风险，使得参数校验逻辑无法做到全局统一审计。

## 单工具与分层判定（Single Tool with Hierarchical Judge）方案

为了消除上述失效模式，本插件采用了“单工具入口 + 分层判定网络”的架构组合。

### 1. 签名极致收敛

插件仅向 Agent 暴露一个极简工具：

```json
{
  "name": "hindsight",
  "description": "唯一的 Hindsight 记忆与知识库操作入口。传入你的自然语言意图（intent），系统会自动完成分类、参数校验与执行。",
  "parameters": {
    "type": "object",
    "properties": {
      "intent": {
        "type": "string",
        "description": "你的自然语言操作意图。例如：'搜索关于向量索引的配置规范'、'把刚才的架构选型结论保存下来'、'查看知识库树结构'。"
      },
      "meta": {
        "type": "object",
        "description": "可选的显式辅助参数。例如提供目标路径 target、指定保存内容 sources 等。"
      }
    },
    "required": ["intent"]
  }
}
```

- 该工具在 Agent 上下文中的定义开销仅为 85 个 Token。
- Agent 在产生任何涉及“记忆”、“查询先例”、“查阅规约”、“保存结论”的需求时，能够立刻且坚定地命中 `hindsight` 工具，消除了犹豫与工具选择分歧。

### 2. 将复杂分类移入系统内部的判定拓扑

工具接收到用户的 `intent` 字符串后，由宿主分配专门的模型在内部执行受控的“分层选择题网络”（Choice Network）。
- 每次判定只有 2 到 4 个绝对互斥的选项。
- 每一个选项都配备了明确的“证据特征（criteria）”。模型只需根据用户原文中包含的具体动作动词和目标实体进行有限分类。
- 这种把“从 26 个动作中直接选一个”拆解为“先分读写、再分形态、再定动作”的三层递进树，使得每一次分类的正确率提升到 99% 以上。

### 3. 两种方案的核心指标对比

| 评估维度 | 20+ 平铺工具模式 | 单工具 + 分层判定模式 |
|---|---|---|
| **每轮上下文消耗** | 约 3,500 Token（固定开销） | 约 85 Token（极简开销） |
| **Agent 主动调用意愿** | 极低（模型倾向于避开复杂工具列表） | 极高（单一入口，心智模型极轻） |
| **工具选择错误率** | 18%～32%（语义边界模糊导致误选） | < 1%（内部互斥判决树严格推导） |
| **参数幻觉率** | 较高（模型自主填补未知的结构化字段） | 0%（仅提取原文切片，由代码无损装配） |
| **系统可扩展性** | 每次新增 API 均会污染全量上下文 | 新增动作仅扩充内部决策树节点，外部暴露完全稳定 |
