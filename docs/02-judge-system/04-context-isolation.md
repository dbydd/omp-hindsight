# 严格上下文隔离矩阵：路由盲目与自动感知的边界

在系统架构中，存在一个看似对立却极具深意的设计分歧：
- 在单工具 `hindsight` 内部的 Choice 路由网络中，系统对历史对话正文保持**完全的盲目（不可见）**；
- 在运行时的自动 Recall（L2 Turn Recall）机制中，系统却对最近的历史对话进行**深度的多角色扫描与自适应提取**。

本篇文档系统阐述这两种上下文可见性边界的理论依据与隔离矩阵。

---

## 为什么路由判定必须对历史对话保持绝对盲目？

当 Agent 调用 `hindsight` 工具时，判定网络只接收当前的 `intent` 字符串以及显式传入的 `meta` 字典。它完全看不到此前的多轮聊天记录。这种严苛的隔离带来了三项决定性的工程优势：

### 1. 彻底切断历史动词对当前意图的语义污染

在典型的编码对话中，前几轮通常包含了大量密集的工程操作指令。例如：
- 第一轮：“读取 `src/index.ts` 并修改导出函数”
- 第二轮：“运行测试并检查报错”
- 第三轮：“检索关于向量索引的配置规范”

若将前两轮的历史对话作为上下文喂给 Choice 判定网络，第三轮在判定“动作是只读还是写入”时，模型极易被上文中高频出现的“修改”、“运行”等写入动词所干扰，导致将只读检索误判为写操作。保持输入盲目确保判定网络始终聚焦于当下的单次诉求。

### 2. 保证判定过程具有极高的响应速度与极低的计算成本

单次 `hindsight` 调用可能触发 2 到 4 次轻量 Choice 判决。
- 盲目模式下，每道题的输入仅有几十个 Token，分类推理在数十毫秒内即可完成。
- 若携带全量历史对话，每道题都需要加载数千甚至上万 Token 的上下文，不仅使工具执行延迟陡增数秒，而且大幅增加了调用成本。

### 3. 杜绝跨轮次捏造与继承参数

槽位提取只允许从当下的输入切片。如果模型能够阅读历史对话，它会倾向于从三轮前的废弃讨论中提取已经失效的文件路径或实体 ID 填入当前参数，引发隐蔽的业务逻辑错误。

## 历史对话记录在系统中的受限介入点

全流程中，仅有四个明确定义的节点与阶段会接触到历史对话，且各自的形态与可见范围被严格约束：

| 阶段 | 介入节点 | 历史对话正文是否可见 | 允许获取的信息形态与用途 |
|---|---|---|---|
| **来源登记** | `D0`（确定性代码） | **不可见** | 仅当请求显式指定保存当前会话时，登记会话元数据（会话 ID、字符长度、哈希值）。 |
| **形态判定** | `W1`（Choice 节点） | **不可见** | 仅根据元数据标记判断保存来源属于 `inline`、`reference` 还是 `session`。 |
| **槽位装配** | `D2`（确定性代码） | **代码直接读取，模型不看** | 由 TypeScript 代码读取 session 文件，执行 toolFilter 清洗与元数据剥除，生成不可变快照。 |
| **会话持久化** | `flush.decision`（后台判定） | **受限可见（带字符截断）** | 会话结束时，评估当前会话新增的讨论是否具备跨会话持久沉淀的价值。 |

---

## 路由盲目与自动感知的职责分权

两套机制服务于完全不同的系统目标，因此拥有截然相反的上下文策略：

```
[ 单工具路由 Choice 网络 ]                     [ 运行时自动 Recall 引擎 ]
- 目标：将单次自然语言转为精确 API 调用          - 目标：长程自治执行时随需注入经验规范
- 特征：极窄输入、零历史干扰、绝对互斥           - 错误优先、提取当前子规划、动态挂载
- 策略：对历史对话正文保持 100% 盲目            - 策略：深度扫描 user/assistant/tool
```

- **单工具路由追求极致的纯净与收敛**：它只负责解析已经发生的显式指令，上下文越纯净，判定的准确率越接近 100%。
- **自动 Recall 追求敏锐的洞察与赋能**：它负责在没有人类直接干预的长程自治编码中，实时感知助手当前碰到的技术困难，主动调取沉淀在记忆库中的规则递给助手。
