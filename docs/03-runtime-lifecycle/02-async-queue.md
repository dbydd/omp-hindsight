# 异步持久化队列：基于目录原子重命名（claim）的高可靠设计

在 Hindsight 记忆系统中，向记忆库写入内容（Retain）包含文本分块、高维向量嵌入计算、实体消歧与图谱构建等密集计算，单次耗时在 5 到 30 秒之间。

本系统采用基于本地磁盘的异步持久化队列，将写入与 Agent 的即时推理彻底解耦，并利用 POSIX 文件系统的目录原子重命名机制实现轻量、无锁且高可靠的任务调度。

---

## 写入管道的轻量条目设计（自包含 Tool Entry）

在正交职责划分下，系统彻底摒弃了向记忆库全量倾倒会话流水账的反模式（会话过程由 omp 原生的 `history://` 完整承载）。

因此，Hindsight 的写入管道无需处理庞大繁杂的会话重解析，而是专注于**高价值已确认条目的可靠交付**：

```
                 【高价值写入触发】
        (显式决策保存、项目规约沉淀、提炼经验)
                         │
                         ▼
             [ 自包含条目 (Tool Entry) ]
        - 完整序列化 content / tags / docId / scopes
        - 计算不可变数据哈希锁定
                         │
                         ▼
         【本地磁盘队列目录：.omp/queue/pending/】
                         │
                         ▼
        【后台消费者使用 rename 原子抢锁认领】
                         │
                         ▼
         【异步推送到远端 Hindsight 实例】
```

### 存储内容与不变性
- **自包含快照**：完整记录待保存的正文（content）、标签（tags）、上下文说明（context）、文档 ID 以及可观察范围（observationScopes）。
- **确定性与无依赖**：条目在写入磁盘的瞬间即固化为标准 JSON 文件。不依赖会话文件的实时变化，也不受后续交互内容滚动的影响。

## 基于目录原子重命名（Atomic Rename Claim）的调度机制

为了避免引入复杂的外部队列中间件（如 SQLite、Redis 等），队列完全构建于操作系统的本地文件系统之上。

### 1. 目录结构划分
队列在项目根目录（或全局目录）下的 `.omp/queue/` 中维护三个状态子目录：
- `pending/`：新提交的待处理任务条目。
- `inflight/`：已被某个工作线程认领并正在上传的任务，按认领编号隔离（例如 `inflight/<claim_id>/`）。
- `failed/`：重试次数超限或发生不可恢复错误的条目。

### 2. 原子重命名实现零锁抢占
当消费者线程准备处理任务时，它不使用任何内存锁或文件锁，而是直接调用 POSIX 标准的 `fs.rename` 操作：

```ts
// 将条目从 pending 目录原子移动到专属于当前认领者的 inflight 目录中
const claimDir = `inflight/${claimId}`;
await fs.mkdir(claimDir, { recursive: true });
await fs.rename(`pending/${entryId}`, `${claimDir}/${entryId}`);
```

- **操作的原子性保障**：在 POSIX 兼容的文件系统中，同一文件系统内的目录重命名操作是由内核保证原子执行的。即使存在多个进程或并发线程同时尝试认领同一个 `entryId`，操作系统的文件系统调度确保恰好只有一个线程能够执行成功，其余线程会收到 `ENOENT` 错误并安全跳过。
- **绝不死锁**：系统不需要处理锁文件的创建、刷新与释放竞争，彻底消除了由于进程意外退出导致的死锁隐患。

### 3. 崩溃恢复与孤儿条目回收
在后台消费者启动或执行心跳检测时，系统会自动扫描 `inflight/` 目录中的所有存量条目：
1. **检查认领者进程（PID）存活状态**：读取任务元数据中记录的 PID。若该进程已在操作系统中消失，说明前序处理流程异常崩溃。
2. **检查任务超时时间**：若条目的认领时间已经超过预设的阈值（例如 5 分钟），系统判定该任务执行挂起。
3. **安全释放回队列**：一旦确认条目变成孤儿状态，恢复逻辑自动执行 `rename` 将其移回 `pending/` 目录，等待下一轮重新调度投递。

## 会话压缩（Compaction）的关键时机保障

在长程编程会话中，当上下文长度逼近模型极限时，omp 宿主会触发会话压缩机制（Session Compaction），将早期对话合并为一段紧凑的摘要。

本插件的队列与会话压缩事件深度绑定：
- 在压缩操作真正执行之前的瞬间，插件的 `session_compact` 钩子会强制发起一次**同步刷新（Flush）**。
- 这确保了即将被宿主压缩裁剪掉的原始长对话历史，已经在第一时间被全量解析并稳妥投递到本地队列中，随即入库保存。
- 这一机制确保了记忆系统始终拥有比当前会话窗口更长远、更完整的全量认知资产。
