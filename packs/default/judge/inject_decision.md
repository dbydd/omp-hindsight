# Instructions
自动召回刚取回一批候选记忆，你决定这一轮要不要把它们放进模型的上下文。

判断依据是候选与「现在正在做什么」的关系，不是相似度分数。分数衡量字面接近，你衡量候选能否改变下一步动作。state.focus 提供触发点 trigger、当前查询 query、任务上下文 task_context 与本会话已注入次数 injected_this_session；候选摘要在 ground_truth 里。

两个成本要权衡：该给的不给，模型会重复踩坑或重新推导已定的事；不该给的硬给，会占掉上下文、把注意力引偏，甚至用一条脏记忆误导它。

# Criteria

## inject
候选能直接影响下一步动作，至少满足其一：
- 它是模型此刻缺、且自己推不出来的事实：已拍板的决策、实测读数、被否决的方案、踩过的坑及处理方式。
- 模型正卡在报错、测试失败或行为不符预期上，候选命中同类问题的根因或解法。
- 用户刚派下新任务，候选携带其前置约束：不许动的文件、必须遵守的流程、已定的术语或接口。
- 判据可概括为：不知道这条，模型接下来很可能做错一件具体的事。

## skip
候选对当前动作没有增量，命中以下任一情况：
- 同名术语撞车：代码里的 model 与机器学习模型、项目名 graph 与图算法、库名 memory 与记忆库，字面相同但讲的是两件事。
- 模型已经在用同一条记忆：本轮或上一步已出现它的结论，或本会话已多次注入同一内容，再给只是复读。
- 候选是操作流水而非知识：「用户要求把 X 入库」「记得保留名字 Y」「User asked to retain…」这类把指令或回执当成的事实，不指导任何下一步。
- 候选属于另一个项目、另一条任务线，纯属字面命中。
- 一批宽召回里没有一条真正对得上当前动作：宁可不给，也不要用边缘相关的内容填满上下文。

触发点差异：turn-end 时模型刚完成一步、未必还有下一步，注入一条弱相关记忆会平白再开一轮，此时对「能否改变下一步动作」要更严格；prompt 触发时用户刚提出任务，相关的前置约束值得给。
